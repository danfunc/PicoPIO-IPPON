# 次段階 (4b: BMC上へのファームウェア転送プロトコル移植) 向け設計メモ

- 作成日: 2026-09-21
- 作成者: Gemini (下層担当)
- 目的: Shizuku (`modules/pico_sdk_support/objects/ota.cpp`) のOTA設計を分析し、BMC (RP2350 1-wire P2P半二重通信) 上で数百KBのファームウェアイメージを安全かつ高速に転送するためのプロトコル設計指針を考察・提言する。
- **注意: 本書はShizukuの実装の直接転記ではなく、BMCの物理的・通信的制約（最大ペイロード128B、半二重ターンアラウンド、DMAリングバッファ等）を踏まえた独自の考察・分析である。**

---

## 1. 物理制約とレイヤ構造のギャップ

### 1.1 パケット長とFlash最小単位の比較
- **BMC パケット仕様**:
  - 最大ペイロード長: **128 バイト**
  - フレーム保護: CRC16-CCITT (2バイト)、ハードウェアパリティ、ビット同期プリアンブル、ポストアンブル
  - 通信方式: 1-wire 半二重 (Half-Duplex) P2P
- **RP2350 Flash (QSPI W25Q32等) 仕様**:
  - ページプログラム最小単位: **256 バイト** (`FLASH_PAGE_SIZE`)
  - セクタ消去最小単位: **4096 バイト (4 KB)** (`FLASH_SECTOR_SIZE`)
  - ブロック消去単位: **65536 バイト (64 KB)** (`FLASH_BLOCK_SIZE`)

### 1.2 構造的ギャップ
1つのFlash消去セクタ (4096B) を転送するためには、BMCパケットが最低 **32パケット** 必要となる。
また、Flash書き込み最小単位 (256B) に対しても、BMCパケットは2パケット分を要する。
このため、BMCパケット層 (トランスポート層) の上に、セクタ単位を扱う **OTAチャンク層 (セッション/アプリケーション層)** を設ける階層化設計が不可欠となる。

---

## 2. チャンクヘッダ形式の考察

### 2.1 Shizuku (BLE/UART OTA) のアプローチ
ShizukuのXNORプロトコルでは、4096Bセクタごとに以下の16バイト自己同期ヘッダを付与している:
```
[u32 magic 'XNCK'][u16 seq][u16 len][u32 crc32(payload)][u16 rsv][u16 crc16(hdr)]
```
- **自己同期 (Self-synchronizing)**: 通信路のバイト化けや同期ずれが発生しても、ヘッダのCRC16およびMagicをスキャンすることで次チャンクの先頭へ自動復帰できる。
- **1チャンク = 1セクタ (4096B)**: Flashの消去最小単位と転送単位が完全に1:1で一致しており、再送時に「セクタ消去→再書き込み」をそのまま行える。

### 2.2 BMC上でのヘッダ設計の選択肢

#### 案A: 4096BチャンクをBMCパケット32個にカプセル化 (フラグメンテーション方式)
- アプリケーション層で 16Bヘッダ + 4096Bデータ = 4112B のチャンクを構成し、トランスポート層で 128B x 33 パケットに分割して送信する。
- **利点**: Shizukuの構造をそのまま抽象化でき、上位層のロジックがシンプル。
- **欠点**: 1パケットが欠落した場合に4096B全体を再送するか、あるいはパケット番号 (0..32) を管理する二重ヘッダが必要になりオーバーヘッドが増大する。

#### 案B: BMCパケットヘッダにセクタIDとサブパケット番号を直接埋め込む (推奨)
- BMCパケットの128Bペイロード内に以下の4バイトOTAヘッダを設ける:
  ```
  [u16 sector_seq][u8 sub_seq (0..31)][u8 flags] + [124B data]
  ```
  ※または、セクタ末尾パケット (sub_seq=32) にセクタ全体のCRC32 (4バイト) を格納。
- **利点**:
  - 1パケット単位で欠落を追跡でき、欠落した128Bパケットだけをピンポイントで再送可能。
  - セクタの組み立てを受信側のSRAMバッファ (4KB) 上で直接インプレースに行える。
  - BMC自体がパケット単位でプリアンブル同期・CRC16・パリティチェックを備えているため、バイトストリーム型のスキャン (CSEEK) が不要。

## 3. 再送制御: 一括送信＋ビットマップ欠落問い合わせ方式の評価

### 3.1 半二重BMCにおけるACK方式の比較

1. **パケット毎 ACK/NACK 方式 (Stop-and-Wait)**:
   - 128B送るごとにGPIO方向をTX→RXに切り替え、相手のACKを待ち、再びTXに切り替える。
   - BMCの通信速度が例えば 1Mbps〜2Mbps の場合、パケット転送時間はおよそ 0.5ms〜1ms。
   - ターンアラウンド遅延（方向切り替え、同期プリアンブル、タイムアウト余裕）が 0.5ms〜1ms かかると、**実効スループットが半分以下に激減**する。
2. **一括送信＋ビットマップ問い合わせ方式 (Shizuku XNOR流用、推奨)**:
   - 送信側は、1ラウンドあたり数十〜数百パケット（例: 64KB = 16セクタ = 512パケット、またはイメージ全体）を一方向にノーウェイトで連続送信する。
   - 受信側は、届いたパケットの `(sector_seq, sub_seq)` をビットマップに記録する（壊れたパケットはBMC層のCRC16で弾かれるため記録されない）。
   - 送信側がラウンド終了パケット (`flags = FIN` または `QUERY_SEQ`) を送ると、初めて通信方向を切り替え、受信側が「未受信パケットのビットマップ」を返送する。
   - 送信側は欠落パケットのみを再送する。

### 3.2 ターンアラウンド回数の削減効果
384KB (3072パケット) の転送において:
- パケット毎ACK: ターンアラウンド **3072 回**。
- ビットマップ方式 (64KBブロック単位で問い合わせ): ターンアラウンドわずか **6 回** (再送ラウンド含めても10回未満)。
半二重1-wireにおいて、この差はスループットに決定的な影響を与える。

## 4. Flash 操作の規律と CPU 停止時間 (リアルタイム性の維持)

### 4.1 `flash_safe_execute` によるCPUストールの問題
- `flash_safe_execute` コールバック実行中は、**割り込みが全面禁止**され、CPUはFlash操作完了までビジーループする。
- 4KBセクタ消去には数ms〜十数ms、64KBブロック消去には数十ms〜百ms以上要する可能性がある。
- **通信への影響**:
  - もしパケットを受信しながらその場でFlash消去を行うと、CPUが停止している間にDMAリングバッファがオーバーランし、後続のパケットを大量に失う（カスケード破綻）。

### 4.2 推奨アーキテクチャ: 3段階パイプライン

Flashの停止時間とBMC受信の整合を取るため、以下の規律を提案する:

```
[Phase 1: 事前一括消去 (Pre-erase)]
  転送シーケンス開始時、ホストから「START_OTA (size=384KB)」を受信。
  通信が止まっている間に、対象ステージング領域 (64KB x 6ブロック) を先行して全消去。
  ※ 64KBブロック消去はセクタ消去の16倍速く、消去による総停止時間を最小化できる。

[Phase 2: ストリーミング受信 & 4KB RAMバッファリング]
  送信側がパケットを一括送信。
  受信側はSRAM上の 4KB ワークバッファにセクタを蓄積。
  4KB溜まった時点で、通信の隙間（またはセクタ完了ハンドシェイク）で 4KB書き込み を実行。
  ※ 事前に消去済みであるため、ここでは書き込み (`flash_range_program`) のみで済む。
  ※ 256Bページ書き込みの停止時間は数百us、4KB書き込みでも数ms程度であり、オーバーランのリスクが劇的に下がる。

[Phase 3: 最終検証 (XIP Readback & CRC32)]
  全パケット受信・書き込み完了後、送信側からのQUERYに対し、受信側がFlash (XIP) から全データを読み出してCRC32を検証。
  結果を返信し、一致していればコミット準備完了とする。
```

## 5. まとめと次段階 (4b) への提言

1. **事前消去 (Pre-erase) の採用**:
   - 転送中のFlash消去はDMAオーバーランの主因となるため、セッション開始時に64KBブロック消去で一括先行消去する。
2. **128Bパケットへのセクタ/サブシーケンス付与**:
   - BMCのCRC16を活かし、128Bパケット単位でインデックス管理を行う。
3. **一括送信＋ビットマップ問い合わせ**:
   - 半二重通信のターンアラウンド損失を回避するため、Stop-and-Waitは避け、ブロック単位の一括送信とビットマップ再送を採用する。
4. **本ベンチマーク (B-4) 実測値のフィードバック**:
   - 本ベンチマークで測定される「4KB書き込み時間」「最大CPU停止時間」を基に、Phase 2におけるパケット間インターバル（送信側のペーシング）やDMAリングバッファの必要サイズを確定する。
